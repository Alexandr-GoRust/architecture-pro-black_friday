## Задание 7. Схемы коллекций и выбор шард-ключей

### Общие принципы выбора шард-ключа

1. Ключ должен обеспечивать **равномерное распределение** документов по шардам (хэшированные ключи) — монотонно растущие или «популярные» значения (id, дата, категория) создают hot spot.
2. Ключ должен соответствовать **основному паттерну доступа**: запросы по шард-ключу попадают в один шард (targeted), все прочие — scatter-gather по всем шардам.
3. Ключ нельзя поменять после создания (без пересборки коллекции) — выбор принимается по бизнес-операциям.

### Коллекция `products`

Схема документа:

```javascript
{
  _id: ObjectId,              // уникальный идентификатор товара
  name: "Смартфон X",         // наименование
  category: "Электроника",    // категория
  price: 59990,               // цена
  stock: {                    // остатки по геозонам
    "Москва": 50,
    "Екатеринбург": 30
  },
  attributes: { color: "чёрный", size: null }  // доп. атрибуты
}
```

Шард-ключ: `{ _id: "hashed" }`.

Обоснование:

- **Главная точечная операция** — обновление остатков при покупке (`updateOne({_id}, {$inc: {...}})`) и страница товара (`findOne({_id})`) — оба запроса содержат `_id`, при хэшированном ключе попадают ровно в один шард.
- **Категорию нельзя брать ключом**: она распределена неравномерно — «Электроника» собирает 70% запросов (кейс задания 8), диапазонное шардирование по категории создаст перегруженный шард.
- Хэш по `_id` равномерно размазывает товары по шардам независимо от популярности категорий.
- Риск: поиск «по категории + диапазону цен» не содержит шард-ключа → scatter-gather (запрос идёт во все шарды и мержится). Это осознанный компромисс: каталог листируется постранично и кешируется (Redis/CDN), а критичные точечные операции остаются быстрыми.

### Коллекция `orders`

Схема документа:

```javascript
{
  _id: ObjectId,              // уникальный идентификатор заказа
  customer_id: "u-83421",     // идентификатор клиента
  created_at: ISODate,        // дата и время оформления
  items: [                    // список товаров с ценой
    { product_id: ObjectId, price: 59990, quantity: 1 }
  ],
  status: "paid",             // статус заказа
  total: 59990,               // общая сумма
  geo_zone: "Москва"          // геозона заказа
}
```

Шард-ключ: `{ customer_id: "hashed" }`.

Обоснование:

- **Основной паттерн чтения** — «история заказов конкретного пользователя» (`find({customer_id})`): при ключе по `customer_id` вся история клиента лежит в одном шарде, запрос точечный и быстрый.
- Создание заказа — вставка с известным `customer_id`, тоже точечная.
- Хэш равномерно распределяет клиентов по шардам (у крупных клиентов и «ботов» не появится выделенный шард).
- `_id` не подходит как ключ: поиск статуса заказа по `_id` был бы точечным, но история клиента (главная операция) стала бы scatter-gather.
- Риск: запрос статуса заказа «в лоб» по `_id` идёт во все шарды. Смягчение: статус всегда запрашивается в контексте клиента (сайт знает `customer_id`); при необходимости заводится «тонкая» служебная коллекция `order_status_index {_id, customer_id}`. Аналитика по всем заказам (редко, batch) — scatter-gather допустим.

### Коллекция `carts`

Схема документа:

```javascript
{
  _id: ObjectId,                          // уникальный идентификатор корзины
  owner_id: "u-83421",                    // вычисляемый владелец: user_id или "s:<session_id>"
  user_id: "u-83421" | null,              // для авторизованных
  session_id: "sess-a1b2" | null,         // для гостей
  items: [ { product_id: ObjectId, quantity: 2 } ],
  status: "active",                       // "active" | "ordered" | "abandoned"
  created_at: ISODate,
  updated_at: ISODate,
  expires_at: ISODate                     // TTL: автоматическая очистка старых корзин
}
```

Шард-ключ: `{ owner_id: "hashed" }`, где `owner_id = user_id` для авторизованных и `owner_id = "s:" + session_id` для гостевых корзин (вычисляется приложением при создании).

Обоснование:

- Оба рабочих запроса («текущая корзина гостя» по `{session_id, status}` и «текущая корзина пользователя» по `{user_id, status}`) превращаются в точечный запрос по `owner_id` — один шард.
- Хэш равномерно распределяет и гостевые, и пользовательские корзины.
- Слияние гостевой корзины в пользовательскую при логине — два точечных чтения/записи (максимум два шарда), оформляется транзакцией.
- TTL-очистка: индекс `{expires_at: 1}, {expireAfterSeconds: 0}` — MongoDB удаляет истёкшие корзины фоновым таск-ом, отдельный cron не нужен.
- Риск: владельца нельзя «переместить» (гость залогинился — корзины две, они сливаются бизнес-логикой), это соответствует операциям задания.

### Команды включения шардирования

```javascript
sh.enableSharding("shop")

sh.shardCollection("shop.products", { _id: "hashed" })
sh.shardCollection("shop.orders",   { customer_id: "hashed" })
sh.shardCollection("shop.carts",    { owner_id: "hashed" })

// индексы под операции (создаются ДО шардирования)
db.products.createIndex({ category: 1, price: 1 })   // листинг с фильтром по цене
db.orders.createIndex({ customer_id: 1, created_at: -1 })
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })  // TTL
```

## Задание 8. «Горячие» шарды: метрики и устранение дисбаланса

### Метрики мониторинга

| Группа | Метрика | Источник | Порог алерта |
|---|---|---|---|
| Распределение данных | Количество чанков на шард; отклонение от среднего | `sh.status()`, `db.collection.getShardDistribution()` | разброс > 20% от среднего |
| Распределение данных | Размер данных/индексов на шард | `getShardDistribution()` | аналогично |
| Нагрузка | Операции чтения/записи в секунду на шард | `db.serverStatus().opcounters`, `mongostat` | один шард > 2× среднего |
| Нагрузка | Сетевой трафик на шард | `mongostat`, метрики ОС | аналогично |
| Задержки | p95/p99 latency операций по шардам | `db.adminCommand({top: 1})`, APM | p99 > SLA (например 100 мс) |
| Ресурсы | CPU, IOPS, использование диска | метрики ОС/облака | > 70–80% |
| Кеш WiredTiger | cache hit/miss, eviction | `serverStatus().wiredTiger.cache` | рост misses |
| Балансировщик | Число миграций чанков, их длительность | `sh.isBalancerRunning()`, логи balancer | миграции в пик нагрузки |
| Соединения | Количество подключений на шард | `serverStatus().connections` | приближение к лимиту |

Примеры команд съёма метрик:

```javascript
sh.status()                                  // карта чанков по шардам
db.products.getShardDistribution()           // данные/нагрузка по шардам
db.serverStatus().opcounters                 // операции по типам
db.adminCommand({ top: 1 })                  // время операций по коллекциям
```

### Действия при обнаружении дисбаланса

1. **Включить и настроить балансировщик** (автоматическое выравнивание чанков):

```javascript
sh.startBalancer()
// окно балансировки — только ночью, чтобы миграции не мешали пиковому трафику
db.settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "02:00", stop: "06:00" } } },
  { upsert: true }
)
```

2. **Разделить горячие чанки вручную** (`sh.splitAt`) — если популярная категория «Электроника» сидит в одном чанке диапазонного ключа:

```javascript
sh.splitAt("shop.products-category_\"Электроника\"", { category: "Электроника", _id: MinKey })
```

3. **Пересмотреть шард-ключ при проектировании** — хэшированные ключи (см. задание 7) не создают hot spot по определению; для уже работающей диапазонной коллекции — постепенная миграция в новую коллекцию с хэш-ключом (`$merge` + переключение записи).

4. **Экстренная ручная миграция чанка** с перегруженного шарда:

```javascript
sh.moveChunk("shop.products", { category: "Электроника" }, "shard3")
```

5. **Зонное шардирование (zone sharding)** — выделенные шарды под горячую нагрузку: горячая категория живёт на мощных узлах, остальные — на обычных:

```javascript
sh.addShardToZone("shard-hot", "hot")
sh.updateZoneKeyRange("shop.products",
  { category: "Электроника", _id: MinKey },
  { category: "Электроника", _id: MaxKey },
  "hot")
```

6. **Разгрузка чтения** — read preference `secondaryPreferred` для каталога (детали — задание 9), кеширование горячих страниц в Redis/CDN.

7. **Горизонтальное наращивание** — добавление шарда: балансировщик сам отсипает часть чанков; добавлять в окно минимальной нагрузки и с предзаготовленным `chunkSize` (увеличение `chunkSize` в `config.settings` уменьшает число миграций).

## Задание 9. Чтение с реплик и консистентность

Обозначения: **P** — только primary, **S** — можно со secondary. Задержка указана как допустимый replication lag для операций на secondary (`maxStalenessSeconds`).

| Коллекция | Операция чтения | Узел | Допустимый lag | Обоснование |
|---|---|---|---|---|
| products | Листинг каталога, поиск по категориям/цене | S | ≤ 10 с | Секундное устаревание цены/наличия в списке терпимо; точные остатки проверяются при оформлении |
| products | Страница товара (описание, атрибуты) | S | ≤ 10 с | Контент меняется редко |
| products | **Остаток при оформлении заказа (перед списанием)** | **P** | — | Риск продажи недоступного товара; проверяется в одной транзакции со списанием |
| orders | История заказов клиента (старые заказы) | S | ≤ 5 с | Устаревание на секунды не мешает просмотру истории |
| orders | **Статус только что оплаченного заказа** | **P** | — | Read-your-writes: клиент сразу после оплаты должен видеть новый статус, устаревший статус вызовет панику и тикеты |
| carts | **Чтение активной корзины** | **P** | — | Read-your-writes: после добавления товара страница перезагружается — пропавший из корзины товар = потерянная продажа |
| carts | Аналитика по abandoned-корзинам | S | ≤ 60 с | Фоновая аналитика, свежесть не критична |

Формулировки правил:

- **Запись — всегда через primary** (в шардированном кластере — через primary Replicaset соответствующего шарда).
- На secondary уходят только операции, для которых бизнес терпит **eventual consistency**: каталог, описание товаров, исторические данные, аналитика.
- Операции с требованием **«чтение своих записей» (read-your-writes)** — корзина и статус свежего заказа — читают только с primary: задержка репликации напрямую бьёт по конверсии.
- Настройка чтения со secondary: `readPreference=secondaryPreferred&maxStalenessSeconds=10` в строке подключения для «каталожных» сервисов; сервис корзины/заказов использует primary по умолчанию.
- Допустимая задержка репликации кластера — алерт при lag > 10 с (мониторинг `rs.printSecondaryReplicationInfo()` / `replSetGetStatus`); при систематическом лаге выше порога — вертикальное усиление secondary или уменьшение доли асинхронных чтений.

## Задание 10. Миграция на Cassandra

### 10.1. Какие данные переносим

Критерии Cassandra: экстремальная скорость записи/чтения по ключу, геораспределение (leaderless), равномерность (consistent hashing + vnodes), ценой — ослабленная согласованность (eventual) и отсутствие многосерверных ACID-транзакций.

| Данные | Верdict | Причина |
|---|---|---|
| **Пользовательские сессии** | ✅ Cassandra | Огромный поток записи/чтения по ключу сессии, данные короткоживущие (TTL из коробки), устаревание на секунды безвредно |
| **События активности (просмотры товаров, клики)** | ✅ Cassandra | Максимальная скорость записи в пик (50 000 req/s), append-only, аналитика терпит eventual consistency |
| **Активные корзины** | ✅ Cassandra | Доступ строго по ключу владельца, TTL для брошенных корзин; компенсация конфликтов через LWW-таймстемпы обновлений |
| **Счётчики популярности товаров** | ✅ Cassandra |	counter-тип, асинхронные инкременты, точность «в итоге» достаточна |
| Заказы (транзакции: заказ + списание остатков) | ❌ остаёмся на MongoDB | Нужны ACID-транзакции и строгая согласованность при списании; потеря/задвоение заказа недопустимы |
| Остатки товаров (stock) | ❌ остаёмся на MongoDB | Конкурирующие точечные обновления, риск перепродажи при eventual consistency |
| Персональные/платёжные данные | ❌ остаёмся в основной БД | Требования целостности и аудита |

### 10.2. Концептуальная модель (partition key + clustering)

```sql
-- Пользовательские сессии: точечный доступ по сессии, авто-TTL
CREATE TABLE sessions (
    session_id uuid,
    user_id text,
    data text,
    expires_at timestamp,
    PRIMARY KEY (session_id)
) WITH default_time_to_live = 86400
   AND comment = 'Сессии: точечное чтение/запись по session_id';

-- События просмотров товара: временной ряд, time-bucket против горячих партиций
CREATE TABLE product_views (
    product_id uuid,
    bucket_ts timestamp,          -- корзина времени (час), разбивает поток по партициям
    event_ts timestamp,           -- clustering key: сортировка внутри партиции
    user_id uuid,
    PRIMARY KEY ((product_id, bucket_ts), event_ts)
) WITH CLUSTERING ORDER BY (event_ts DESC)
   AND default_time_to_live = 2592000;

-- Активные корзины: строки корзины по владельцу
CREATE TABLE cart_items (
    owner_id text,                -- user_id или "s:<session_id>"
    product_id uuid,
    quantity int,
    updated_at timestamp,
    PRIMARY KEY ((owner_id), product_id)
) WITH default_time_to_live = 1209600;   -- авто-очистка брошенных корзин (14 дней)

-- Счётчик популярности товара
CREATE TABLE product_popularity (
    product_id uuid PRIMARY KEY,
    views counter
);
```

Обоснование ключей:

- **`sessions`**: partition key `session_id` — равномерное распределение (случайные uuid), точечный доступ, TTL встроен.
- **`product_views`**: составной partition key **`(product_id, bucket_ts)`** — решает проблему «горячей партиции» популярного товара (70% трафика): события одного товара разбиваются на часовые корзины, и хэш-распределение разносит их по узлам; clustering `event_ts` сохраняет порядок внутри партиции для диапазонных запросов. Без бакета популярный товар собрал бы гигантскую нечитаемую партицию.
- **`cart_items`**: `(owner_id)` — вся корзина одного владельца в одной партиции: чтение/слияние корзины — одна партиция, одна реплика-группа.
- **Решардинг**: Cassandra использует consistent hashing с **виртуальными нодами** (256 vnode на сервер) — при добавлении узлов перераспределяется лишь небольшая часть токенов, без полной миграции данных (то, что «убило» latency в MongoDB с range-шардированием).

Уровни согласованности: запись `LOCAL_QUORUM` (данные переживут отказ узла), чтение `LOCAL_ONE`/`ONE` для сессий и счётчиков (скорость, eventual допустим), для корзины — `LOCAL_QUORUM` на чтение после записи (read-your-writes).

### 10.3. Стратегии восстановления целостности по сущностям

| Сущность | Стратегии | Обоснование (latency vs гарантии) |
|---|---|---|
| Сессии | **Hinted Handoff** + **Read Repair** | Читаются часто → Read Repair быстро выравнивает; краткие сбои узлов закрывают хинты (~3 ч хранения). CL ослабленный — задержка важнее |
| События просмотров | **Hinted Handoff** + плановый **Anti-Entropy Repair** (`nodetool repair` раз в неделю, ночью) | Редко читаются поодиночке → Read Repair не сработает; гарантированная сверка всех данных по расписанию. Запись дешёвая, накладные расходы repair терпимы в фоне |
| Корзины | **Hinted Handoff** + **Read Repair** (+ LOCAL_QUORUM) | Частые чтения и обновления → рассинхрон ловится чтением; кворум на запись страхует от потери; LWW по `updated_at` разрещает конфликты |
| Счётчики популярности | Hinted Handoff; периодический repair | Точность «в итоге» достаточна; counter-тип сам синхронизируется репликами |

Компромисс сформулирован: чем чаще данные читаются — тем больше работы делает бесплатный Read Repair; редко читаемые, но обязательные к целостности данные — плановый Anti-Entropy Repair (самый тяжёлый, поэтому ночью и по расписанию); кратковременные сбои во всех случаях закрывает Hinted Handoff.

## Сводка метрик мониторинга и действий (общая для заданий 8–10)

| Симптом | Метрика-триггер | Действие |
|---|---|---|
| Дисбаланс шардов | чанки/данные на шард, разброс > 20% | окно балансировщика → splitAt горячих чанков → zone sharding |
| Перегрузка одного шарда | ops/s или p99 на шарде > 2× среднего | ручной moveChunk, зонирование горячей категории, кеш горячих запросов |
| Lag репликации > 10 с | replSetGetStatus | усилить secondary, снизить долю secondaryPreferred-чтений |
| Кассандра: рост устаревших чтений | histogram чтений, repair-отчёты | внеплановый nodetool repair, проверить hinted_handoff_window |
| Кеш не спасает | cache hit-rate < 90% | пересмотреть TTL и ключи кеша, поднять память Redis |
